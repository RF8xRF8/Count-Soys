拍照计数系统（Photo Count）项目开发说明书

本文档面向接手开发的 AI 或工程师。请严格按本文档实现，遇到文档未覆盖的细节，优先选择简单、可运行、易维护的方案，并在 README 中记录决策。

一、项目背景与目标

1. 背景
实验室场景下需要频繁对药片、豆子、细胞等离散物体进行计数。传统人工计数效率低、易出错。本系统提供「手机或电脑拍照 → 上传 → 服务端自动计数 → 返回打点编号图 + 计数结果」的闭环。

2. 目标
- 用户通过浏览器拍照或上传图片，服务端在 1～2 秒内返回标注图与计数。
- 系统不开放注册，所有账号由管理员在后台创建。
- 支持多账号登录、JWT 鉴权，区分普通用户与管理员。
- 记录每次计数任务，提供个人与全局使用统计。
- 第一版算法使用分水岭（Watershed），后续可平滑替换为 YOLO 或 Cellpose，不影响上层架构。

3. 非目标（本期不做）
- 视频流计数
- 微信小程序
- 移动端原生 App
- 实时 WebSocket 推送
- GPU 推理
- 用户自助注册
- 用户自助找回密码（密码重置由管理员完成）

五、数据库设计

1. users 表
- id，BIGINT 主键，自增
- username，VARCHAR(64)，唯一，登录名
- email，VARCHAR(128)，唯一
- password_hash，VARCHAR(255)，bcrypt
- role，VARCHAR(16)，user 或 admin，默认 user
- status，SMALLINT，1 正常，0 禁用
- daily_quota，INT，每日计数次数上限，默认 100
- created_by，BIGINT，创建该用户的管理员 id，系统初始化管理员可为空
- created_at，TIMESTAMP
- updated_at，TIMESTAMP
- last_login_at，TIMESTAMP

2. tasks 表
- id，BIGINT 主键
- task_id，VARCHAR(32)，唯一，UUID hex
- user_id，BIGINT，外键 users.id
- mode，VARCHAR(16)，pills 或 beans 或 cells
- params_json，TEXT，用户传入参数快照
- original_path，VARCHAR(255)，原图相对路径
- annotated_path，VARCHAR(255)，结果图相对路径
- count，INT，计数结果
- instances_json，TEXT，每个实例的坐标与面积
- width，INT，处理时图像宽
- height，INT，处理时图像高
- elapsed_ms，INT，服务端耗时
- status，VARCHAR(16)，success 或 failed
- error_msg，VARCHAR(255)，失败原因
- client_ip，VARCHAR(45)
- created_at，TIMESTAMP

索引：user_id、created_at、mode、status。

3. daily_stats 表（可选，或直接聚合 tasks）
- id，BIGINT 主键
- stat_date，DATE
- user_id，BIGINT，外键
- mode，VARCHAR(16)
- total_count，INT，任务数
- success_count，INT，成功数
- failed_count，INT，失败数
- sum_elapsed_ms，BIGINT，总耗时
- sum_objects，BIGINT，累计识别物体数

唯一索引：(stat_date, user_id, mode)。
第一版建议直接聚合 tasks 表，简单可靠。

4. refresh_tokens 表（可选）
- id，BIGINT 主键
- user_id，BIGINT，外键
- token，VARCHAR(255)，唯一
- expires_at，TIMESTAMP
- revoked，BOOLEAN
- created_at，TIMESTAMP

六、后端 API 设计

统一前缀：/api
统一响应格式：
{ "code": 0, "message": "ok", "data": { } }
code=0 成功，非 0 失败。HTTP 状态码仍按语义返回 401、403、404、500 等。
分页参数：page、page_size，返回 items、total、page、page_size。

POST   /api/auth/refresh           刷新 access token                公开
POST   /api/auth/logout            登出，撤销 refresh token         登录
GET    /api/auth/me                当前用户信息                     登录
POST   /api/auth/change-password   修改自己的密码                   登录

不提供 /api/auth/register。所有账号由管理员通过 /api/admin/users 创建。

登录请求：
{ "username": "alice", "password": "xxx" }

登录响应：
{
  "code": 0,
  "data": {
    "access_token": "...",
    "refresh_token": "...",
    "token_type": "bearer",
    "expires_in": 7200,

      "id": 1,

七、核心算法实现（分水岭）

放在 app/services/counting.py，接口签名：
def count_objects(img_bgr, mode, params) -> (annotated, instances, warnings)
instances 格式：[{"id": 1, "x": 123, "y": 456, "area": 812}, ...]

参考实现要点：
- 灰度化，GaussianBlur 5x5
- threshold_mode 为 otsu_inv 时用 THRESH_BINARY_INV + OTSU，否则 THRESH_BINARY + OTSU
- 形态学开运算，kernel 3x3，iterations=2
- 膨胀得到 sure_bg
- distanceTransform 得到距离图
- 阈值取 fg_ratio * dist.max() 得到 sure_fg
- unknown = sure_bg - sure_fg
- connectedComponents 得到 markers，markers 加 1，unknown 处置 0
- cv2.watershed 分割
- 遍历 label，面积小于 min_area 的丢弃
- 每个 label 取质心 (cx, cy)，依次编号，写入 instances
- 画点、编号、顶部写 Count=N

图像预处理放在 app/services/image_io.py：
- 用 Pillow 打开，先 ImageOps.exif_transpose 处理手机竖拍方向
- 转 RGB，再转 BGR ndarray
- 长边缩放到 max_side，默认 1600，用 INTER_AREA

八、鉴权与权限

流程：
1. 管理员创建用户，用户拿到初始密码。
2. 用户登录，校验密码，签发 access + refresh。
3. 前端存 token，access 与 refresh 都放 localStorage。
4. 请求拦截器自动加 Authorization: Bearer access。
5. 响应 401 时自动用 refresh 换新 access，refresh 失效则跳登录页。
6. 登出调用 /api/auth/logout，前端清空 token。

权限控制：
- get_current_user 依赖，解析 JWT，查库校验 status=1。
- require_admin 依赖，在 get_current_user 基础上校验 role=admin。
- 资源级权限：任务详情、编辑、删除时校验 task.user_id == current_user.id 或 role == admin。

配额控制：
- 每次 POST /api/count 前，统计该用户当天成功任务数。
- 若大于等于 daily_quota，返回 429 与提示。
- admin 不受配额限制。

Axios 封装要点：
- baseURL 为 /api，timeout 30 秒。
- 请求拦截器读取 auth store 中的 accessToken，加到 Authorization 头。

Pinia auth store 要点：
- state：accessToken、refreshToken、user。
- getters：isLoggedIn、isAdmin。
- actions：setTokens、login、refresh、fetchMe、clear。
- token 持久化到 localStorage。

十三、安全要求

- 密码必须 bcrypt 哈希，禁止明文存储。
- JWT 密钥不得硬编码，必须从环境变量读取。
- 上传文件校验：扩展名白名单 jpg、jpeg、png、webp、bmp；校验 MIME；大小不超过 MAX_UPLOAD_MB；用 Pillow 打开验证是真实图片。
- 文件名一律用 task_id 生成，禁止使用用户原始文件名。
- 路径穿越防护：所有文件路径基于 STORAGE_DIR 拼接后校验前缀。
- CORS 仅允许配置的前端域名。
- 登录失败限流：同一 IP 或用户名 5 分钟内失败 10 次锁定。
- 所有管理接口必须 require_admin。
- 生产环境强制 HTTPS。

十六、验收标准

1. 系统不提供注册入口，账号只能由管理员创建。
2. 用户可登录、登出，token 过期自动刷新。
3. 登录用户上传图片，服务端返回计数与标注图，前端展示。
4. 计数结果写入 tasks 表，历史页可查、可删、可导出 CSV。
5. 个人统计页展示总览、按天趋势、按模式分布。
6. admin 可管理用户、重置密码、查看全局统计。
7. 配额生效，超限返回 429。
8. 所有接口有统一响应格式和错误处理。
9. 单张 2MP 图处理耗时小于 1 秒（4 核 CPU）。
